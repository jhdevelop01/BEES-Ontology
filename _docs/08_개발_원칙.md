## 1. TTL-First 원칙 (최상위 원칙)

### 1.1 Single Source of Truth

```
Brick Schema TTL 파일이 유일한 원본(Single Source of Truth)이다.
Neo4j GraphDB는 TTL로부터 파생된 런타임 엔진이다.
```

- **모든 변경은 TTL 파일에 먼저 적용**한다
- Neo4j는 TTL에서 임포트/동기화하는 **파생 저장소**이다
- TTL과 Neo4j가 불일치하면, **TTL이 정답**이다

### 1.2 변경 워크플로우 (반드시 이 순서)

```
[1] TTL 수정 (ontology/GEC_B_Ontology.ttl)
        ↓
[2] rdflib 파싱 검증 (구문 오류 확인)
        ↓
[3] SHACL 검증 (ontology/GEC_B_SHACL.ttl 대조, Conforms: True 확인)
        ↓
[4] 문서 업데이트 (_docs/history.md, _docs/07_온톨로지_통계_요약.md, CLAUDE.md)
        ↓
[5] Neo4j 동기화 (n10s 재임포트 또는 증분 Cypher)
```

- 1~4 없이 5를 먼저 하지 않는다
- Neo4j에서 직접 노드/관계를 생성하지 않는다 (TTL에 없는 데이터 금지)

### 1.3 Neo4j 직접 수정 금지 사유

| 구분 | TTL 기반 | Neo4j 직접 수정 |
|------|----------|----------------|
| 버전관리 | Git으로 이력 추적 가능 | DB 상태 버전관리 불가 |
| 이식성 | 어떤 GraphDB든 임포트 가능 | Neo4j에 종속 |
| 대통합 | 다른 건물 TTL과 병합 용이 | 사일로 재발생 |
| 검증 | SHACL로 구조적 무결성 검증 | 검증 체계 없음 |
| 재현성 | TTL → 어디서든 동일 그래프 복원 | 백업/복원 복잡 |

## 2. Brick Schema 준수 원칙

### 2.1 네임스페이스

| Prefix | URI | 용도 |
|--------|-----|------|
| `brick:` | `https://brickschema.org/schema/Brick#` | Brick 표준 클래스/프로퍼티 |
| `bldg:` | `https://example.org/gec-b#` | GEC B동 인스턴스 (추후 도메인 변경 예정) |
| `bees:` | `https://example.org/bees#` | 커스텀 클래스/프로퍼티 (28클래스 + 45속성) |

> **대통합 시**: `example.org` → 조직 도메인(예: `samsung.com/bldg/`)으로 일괄 치환

### 2.2 위계 구조

```
Site → Building → Floor → Zone/Room
                        → System → Equipment → Point
```

- 새 인스턴스는 반드시 이 위계 내에 위치해야 한다
- `bldg:GEC_Tower_B` 또는 그 하위에 연결

### 2.3 관계 대칭 원칙

```
hasPart  ↔  isPartOf    (양방향 반드시 동시 작성)
feeds    ↔  isFedBy     (양방향 반드시 동시 작성)
```

- 한쪽만 작성하면 그래프 탐색 시 경로가 끊김
- Neo4j에서도 양방향 관계가 모두 존재해야 정확한 Cypher 쿼리 가능

### 2.4 필수 속성

모든 `bldg:` 인스턴스에 반드시:

| 속성 | 필수 여부 | 용도 |
|------|----------|------|
| `rdf:type` | 필수 | Brick 클래스 지정 → Neo4j 노드 라벨 |
| `rdfs:label` | 필수 | 한글 라벨 → Neo4j 노드 프로퍼티, LLM 자연어 매칭 |
| `bees:hasConfidence` | 필수 | 신뢰도 (confirmed/estimated/inferred) |
| `brick:hasLocation` | Equipment 필수 | 위치 연결 → 공간 기반 쿼리 |
| `brick:isPartOf` | Equipment/Point 필수 | 소속 시스템/장비 연결 |

### 2.5 rdfs:label 작성 규칙

LLM 자연어 쿼리의 핵심 진입점이므로:

- **한국어로 작성** (사용자가 한국어로 질문)
- **직관적이고 구체적으로**: `"B동 5층 UFAD AHU #1"` (O), `"AHU1"` (X)
- **위치 정보 포함 권장**: 층수, 방향 등 포함하면 LLM 매칭 정확도 향상
- 영어 약어는 괄호 또는 혼합 사용 허용: `"B동 칠러 #1 (800RT)"`

## 3. 변경 관리 원칙

### 3.1 변경 단위

| 변경 유형 | 예시 | TTL 수정 방법 |
|-----------|------|--------------|
| 신규 인스턴스 추가 | 새 센서 설치 | rdflib 스크립트 또는 Edit 도구 |
| 관계 추가/수정 | feeds 경로 변경 | rdflib 스크립트 (양방향 동시) |
| 속성값 변경 | 라벨 수정, 용량 변경 | Edit 도구 (단일 변경) |
| 대규모 구조 변경 | 새 시스템 추가, 층 구조 변경 | rdflib 스크립트 + reorganize_ttl.py |

### 3.2 TTL 수정 후 필수 체크리스트

```
[ ] rdflib 파싱 성공 (트리플 수 확인)
[ ] SHACL Conforms: True
[ ] 새 인스턴스에 rdfs:label 있음
[ ] 새 인스턴스에 bees:hasConfidence 있음
[ ] hasPart↔isPartOf 양방향 확인
[ ] feeds↔isFedBy 양방향 확인
[ ] 고아 노드(orphan) 없음 확인
[ ] history.md 업데이트
[ ] 17_통계요약.md 업데이트
[ ] CLAUDE.md 트리플/인스턴스 수 업데이트
```

### 3.3 reorganize_ttl.py 사용 원칙

- rdflib `serialize()`는 주석과 섹션 구조를 파괴함
- 대규모 변경 후에는 반드시 `/tmp/reorganize_ttl.py` 실행하여 섹션 구조 복원
- 소규모 변경(1~3개 엔티티)은 Edit 도구로 직접 수정 가능

## 4. Neo4j 동기화 원칙

### 4.1 임포트 방법

```
TTL → n10s(neosemantics) 플러그인 → Neo4j Property Graph
```

- `n10s` 플러그인 사용하여 RDF/TTL을 Neo4j로 임포트
- 전체 재임포트(full reload) 또는 증분 업데이트(delta) 선택

### 4.2 매핑 규칙

```
[RDF/TTL]                          [Neo4j Property Graph]
─────────────────────────          ─────────────────────────
rdf:type brick:AHU              → (:AHU) 노드 라벨
rdfs:label "B동 5층 AHU #1"     → node.label 프로퍼티
brick:feeds                     → -[:feeds]-> 관계
brick:isPartOf                  → -[:isPartOf]-> 관계
brick:hasLocation               → -[:hasLocation]-> 관계
bees:hasConfidence "confirmed"  → node.hasConfidence 프로퍼티
bees:capacity "800"             → node.capacity 프로퍼티
```

### 4.3 동기화 타이밍

| 상황 | 동기화 방법 |
|------|------------|
| 온톨로지 버전 업그레이드 (v2.0 → v2.1) | 전체 재임포트 |
| 소규모 인스턴스 추가 (1~5개) | 증분 Cypher 또는 재임포트 |
| 구조 변경 (시스템/관계 재편) | 전체 재임포트 |

### 4.4 Neo4j 데이터 검증

동기화 후 확인:
- 노드 수 = TTL 인스턴스 수 (845개 기준)
- 관계 수 ≈ TTL 관계 수 (feeds 169 + isPartOf 418 + hasLocation 391 + ...)
- 한글 라벨 프로퍼티 존재 확인
- 샘플 Cypher 쿼리 실행하여 결과 비교

## 5. 데이터 대통합 원칙

### 5.1 다른 건물 온톨로지 통합 시

```
GEC_B_Ontology.ttl  (bldg: = gec-b#)     ─┐
GEC_A_Ontology.ttl  (bldg-a: = gec-a#)    ├→ 통합 그래프
GEC_C_Ontology.ttl  (bldg-c: = gec-c#)    ─┘
```

- 모든 건물이 동일한 `brick:` 스키마를 사용하므로 자동으로 호환
- 건물별 인스턴스 네임스페이스만 다르게 유지
- `bees:` 커스텀 정의는 공통 모듈로 분리 가능

### 5.2 네임스페이스 마이그레이션

운영 환경 전환 시:

```
개발: https://example.org/gec-b#
운영: https://{조직도메인}/bldg/gec-b#
```

- TTL 파일 내 일괄 치환 (sed 또는 Python)
- Neo4j 재임포트
- 기존 쿼리/코드의 네임스페이스 참조 업데이트

### 5.3 데이터 사일로 방지 규칙

- **새 데이터 소스 연동 시**: 반드시 Brick Schema 클래스에 매핑 후 TTL로 먼저 작성
- **Neo4j에만 존재하는 노드/관계 금지**: TTL에 없으면 Neo4j에도 없어야 함
- **커스텀 확장 시**: `bees:` 네임스페이스에 OWL 클래스/프로퍼티로 정의한 후 사용

## 6. LLM 자연어 쿼리 서비스 관련 원칙

### 6.1 온톨로지 측 책임

온톨로지(TTL)가 보장해야 할 것:

- 모든 인스턴스에 **한글 rdfs:label** (LLM 자연어 매칭용)
- 풍부한 **관계(엣지)** (그래프 탐색 경로 확보)
- 정확한 **rdf:type** (Neo4j 노드 라벨 → LLM이 Cypher 생성 시 사용)
- **관계 대칭** (양방향 탐색 보장)

### 6.2 LLM/애플리케이션 측 책임

온톨로지에 넣지 않아도 되는 것:

- 한영 동의어 사전 → LLM 프롬프트 또는 애플리케이션 레이어
- 쿼리 템플릿 → LLM Few-shot 프롬프트 또는 LangChain 설정
- 사용자 인터페이스 텍스트 → 프론트엔드 레이어

### 6.3 경계 원칙

```
온톨로지 = 건물의 "사실(fact)" + "구조(structure)"
LLM 레이어 = "해석(interpretation)" + "표현(presentation)"
```

온톨로지에 LLM 서비스 로직을 섞지 않는다.

## 7. 검증 명령어 (Quick Reference)

```bash
# TTL 구문 검증
python3 -c "from rdflib import Graph; g=Graph(); g.parse('ontology/GEC_B_Ontology.ttl'); print(f'트리플: {len(g)}')"

# SHACL 검증
python3 -c "
from pyshacl import validate
from rdflib import Graph
d=Graph(); d.parse('ontology/GEC_B_Ontology.ttl')
s=Graph(); s.parse('ontology/GEC_B_SHACL.ttl')
c, _, t = validate(d, shacl_graph=s)
print(f'Conforms: {c}')
if not c: print(t)
"

# 주요 관계 수 확인
python3 -c "
from rdflib import Graph, Namespace
g=Graph(); g.parse('ontology/GEC_B_Ontology.ttl')
BRICK=Namespace('https://brickschema.org/schema/Brick#')
for rel in ['feeds','isFedBy','hasPart','isPartOf','hasLocation','isPointOf']:
    cnt = len(list(g.triples((None, BRICK[rel], None))))
    print(f'  {rel}: {cnt}')
"
```
