## 1. ★ 최우선 교차 이슈 — 시뮬레이션 틱 주기 1초 vs 문서 5초

**가장 중요한 발견이자 단일 결정 포인트.** `srv-c`가 적발: `server-c/app/config.py:23` 기본값이 `SIMULATION_INTERVAL=1.0`이고 `.env`·`docker-compose.yml`에 오버라이드가 없다. 그러나 `CLAUDE.md`·`history.md`·`MEMORY.md`·`openai_service.py` SYSTEM_PROMPT는 모두 **"5초 주기"**로 기술한다.

이 한 줄의 불일치가 **3개 서버에 동시 파급**된다(파이프라인 전체가 문서 가정의 5배 부하로 가동 중):

```
Server C (틱당 ~954 MQTT 발행, 실제 1초)
      │  bees/points/* · bees/devices/* · bees/alarms/*
      ▼
Server A mqtt_service → _event_queue(deque maxlen=500) → SSE 0.5초 배치
      │  ⚠ 1초마다 954 이벤트 버스트 → maxlen=500 초과 시 앞부분 유실 (A P1-E)
      ▼
Server A Frontend useSSE × 2인스턴스 (중복 수신·파싱·setState) (FE P0-1)
      │
      ▼
Server D mqtt_worker → 동기 InfluxDB write (이벤트 루프 블로킹) (D P0-1)
         용량 산정도 "5초=일 1,150만 포인트"인데 실제 1초면 5배
```

**조치(선결)**: 1초가 의도면 전 문서/SYSTEM_PROMPT를 1초로 정정, 5초가 의도면 `config.py`/`.env`에 명시. **이 결정이 C·A·D의 모든 용량·비용 산정의 전제**이므로 다른 어떤 최적화보다 먼저 합의해야 한다.

## 2. 횡단 테마 — 5개 서버에 반복되는 동일 안티패턴

### 테마 A. async 이벤트 루프 블로킹 (`run_in_executor` 전무)
동기 CPU/IO 작업을 async 핸들러에서 직접 호출 → 루프 점유. 코드베이스 전체 `run_in_executor`/`to_thread` 사용 0건.
- **A-Backend**: xlsx/pdf(openpyxl·FPDF), smtplib, 파일 open (`report_service.py:98`, `notification_service.py:105`)
- **C**: 시뮬레이션 생성부 전체가 동기 점유 후 sleep (`engine.py:595-689`)
- **D**: 동기 InfluxDB write + 큰 export 쿼리 (`mqtt_worker.py:478`, `export.py:87`)
- **공통 처방**: 블로킹 구간을 `await asyncio.to_thread(...)`/`run_in_executor`로 오프로드. 가장 저비용·고효과 공통 작업.

### 테마 B. 무제한 인메모리 증가 → OOM 리스크
상한·만료·GC 없는 메모리 구조.
- **A-Backend**: `_report_cache`(바이너리 blob), `_graph_cache`(키 조합 무한) (`report_service.py:50`, `neo4j_service.py:754`)
- **B**: `asyncio.Queue()` maxsize 무제한 (`command_queue.py:58`)
- **D**: `_buffer` 상한 없음, 쓰기 막히면 무한 증가 (`mqtt_worker.py:50`)
- **공통 처방**: maxsize/LRU/TTL-GC 상한 + 초과 시 정책(드롭+카운터 또는 백프레셔) 명시.

### 테마 C. "실패·공격 표면을 숨기는" 패턴
실패를 성공처럼 보이게 하거나, 인증/검증 없이 노출.
- **A-Backend**: `/cypher`·`/chat` 무인증, 정규식 블록리스트 우회 가능, 하드코딩 시크릿 (`ontology.py:55`, `chat.py:52`, `config.py:44`)
- **B**: Server C 호출 실패해도 항상 `success=True` (거짓 성공) (`main.py:497`)
- **D**: 쓰기 실패 시 데이터 조용히 폐기("유실" 로그만), Flux 인젝션 (`mqtt_worker.py:470`, `points.py:115`)
- **공통 처방**: 실제 상태를 응답에 반영(202/503/413), 입력 바인딩/화이트리스트, 인증·rate limit.

### 테마 D. per-request 클라이언트/리소스 재생성
커넥션 풀/드라이버를 재사용하지 않고 매번 생성.
- **A-Backend**: `httpx.AsyncClient` 18곳 per-request (`openai_service.py` 도구 다수)
- **B**: Neo4j 드라이버를 재시도마다 생성/종료 (`neo4j_loader.py:110`)
- **D**: `POST /data/points`마다 write_api 재생성 (`points.py:255`)
- **공통 처방**: lifespan에서 1회 생성한 공유 싱글톤(keep-alive) 재사용.

### 테마 E. Neo4j 조회 비효율 (캐시 부재 / 풀스캔)
- **A-Backend**: `get_graph_data`만 캐시, 토폴로지/fault-impact 등은 매 요청 직격; `/devices/status` 전체 풀스캔+루프내 import (`neo4j_service.py:350`)
- **B**: 라벨 인덱스 못 쓰는 AllNodesScan (`neo4j_loader.py:126`)
- **공통 처방**: 준불변 온톨로지 결과 TTL 캐시 확대, 라벨 기반 MATCH로 스캔 회피.

### 테마 F. 문서-코드 드리프트 (정합성)
- **C**: 틱 1초 vs 5초(§1)
- **A-Backend**: SYSTEM_PROMPT "845 인스턴스/691 포인트/1초" vs 실측 "11,502 트리플/670 포인트" (`openai_service.py:57`)
- **D**: aggregated_365d 주석 "1일 평균" vs 구현 "1시간 평균", InfluxDB OSS Task API 미지원 가능 (`retention.py:7`, `downsampling.py:103`)
- **공통 처방**: 통계/주기를 하드코딩 대신 기동 시 주입, CLAUDE.md "연쇄 업데이트" 체크리스트 강화.

## 3. 통합 실행 로드맵 (권장 순서)

### 0단계 — 선결 (반인시간)
- **틱 주기 1s/5s 확정**(§1) → 전 문서/SYSTEM_PROMPT 동기화. 이후 모든 용량 산정의 기준.

### 1단계 — 보안 P0 (즉시, 저Effort 다수)
1. A-Backend: `/cypher`·`/chat` 인증 부여 + Neo4j 읽기전용 롤/READ 모드 + 채팅 rate limit
2. A-Backend: 하드코딩 시크릿 제거 + fail-fast + JWT 소스 단일화
3. D: Flux 입력 바인딩/화이트리스트 (인젝션 차단)

### 2단계 — 데이터 무손실·가용성 P0
4. D: 동기 write 논블로킹화 + 내장 배치 WriteApi(재시도·백프레셔·write_api 재사용 동반 해결)
5. D: export 진성 스트리밍 + 기간/행 상한 (OOM 방지)
6. B: 재시도 큐 head-of-line blocking 제거 + maxsize 백프레셔 + 거짓 성공 제거

### 3단계 — 실시간 성능 P0~P1
7. A-Frontend: `useSSE` 싱글톤화(Context/외부 스토어) — 연결·상태·리렌더 2배 제거, `pointHistory` 지연 구축, AlarmBanner 구독 분리 (P0 3건 일괄)
8. A-Backend: SSE 클라이언트별 큐 재설계(공유 deque 유실 제거) — FE 싱글톤화와 짝
9. C: 핫 루프 P0 6건(spec/seasonal 등록 시 캐싱, import 제거, lazy debug, isoformat 1회, fault fast-path, weather 캐싱) — 전부 동작 불변·저위험

### 4단계 — 공통 위생 (테마 A~E 잔여)
10. 블로킹 오프로드(A 보고서/메일, C 생성부), 캐시 상한(A), 공유 httpx/드라이버(A·B), Neo4j 캐시·라벨 인덱스(A·B), D 버킷 라우팅·summary 범위 축소

### 5단계 — 구조 변경 (P2, 조건부)
11. C numpy 벡터화 + MQTT 배치 발행(↔ A 구독 동시 변경), D quality/mode 태그→필드, FE SWR/React Query 캐시 도입
