## 0. 이 문서의 관점

개별 서버 이슈는 각 `server-X_optimization.md`에 정리되어 있다. 본 문서는 **서버 경계를 넘는 횡단 패턴**과 **서버 간 의존성**을 기준으로 실행 순서를 정한다. 단일 서버 시야에서는 "보안 1건"이지만, 4서버를 겹쳐 보면 **동일 결함이 3개 서버에 반복**되고 **한 서버의 변경이 다른 서버로 증폭 전파**되는 구조가 드러난다 — 이것이 우선순위 결정의 핵심 근거다.

| 서버 | 역할 | P0 | P1 | P2 | 가장 시급한 1건 |
|------|------|:--:|:--:|:--:|------|

## 1. 횡단 패턴 (Cross-Cutting) — 최우선 처리 대상

### CC-1. 인증/인가 부재 — A·B·D 공통 🔴 (가장 치명적)
플랫폼 전반에 인증이 거의 적용되지 않음. 특히 **제어 평면(B)** 과 **감사 로그(A·D)** 가 무인증인 것이 치명적.

| 서버 | 근거 | 위험 |
|------|------|------|
| A | 19개 중 13개 라우터 무인증(`routers/`). `/api/chat`(chat.py:52), `/api/ontology/cypher`(ontology.py:55) | OpenAI 비용 남용, 그래프 전량 exfiltration |
| B | 전 제어 엔드포인트 무인증, `userId` 본문 무검증(main.py:79·423·816) | 무단 장비 제어, 감사 로그 위조 |
| D | `admin.py` 전체 무인증, `acknowledge_alarm` `acknowledged_by` 기본값 1 | 감사 무결성 붕괴, 무단 알람 확인 |

**통합 처리안**: Server A↔B↔D 공통 서비스 토큰/세션 가드를 FastAPI `Depends`로 일괄 도입. 읽기 전용은 viewer 이상, 쓰기/제어는 role 검증. `userId`/`acknowledged_by`는 본문이 아닌 토큰에서 도출. `audit_log.ip_address`를 `request.client.host`로 실제 기록.
**의존성**: Server A 프론트엔드 호출부(`lib/api.ts`)에 토큰 주입 동기화 필요 → **독립 배포 불가, 4서버 동시 변경**.

### CC-2. 이벤트 루프 블로킹 — C·D 공통 🟠
`async def` 내부에서 동기(blocking) 작업을 직접 수행해 FastAPI 이벤트 루프를 점유.

| 서버 | 근거 | 영향 |
|------|------|------|
| C | 691포인트 생성이 `await` 없이 동기 실행(engine.py:610-679) | 틱 계산 중 `/health`·제어 API 지연 |
| D | 동기 InfluxDB write/query를 핸들러에서 직접 호출(mqtt_worker.py:483, points.py:118 등) | write 중 모든 조회/헬스체크 정지, 동시요청 직렬화 |

**통합 처리안**: 무거운 동기 작업을 `run_in_executor`로 스레드풀 위임(D의 InfluxDB), 또는 청크 사이 `await asyncio.sleep(0)` 삽입(C). D는 InfluxDB 배치 모드(`WriteType.batching`) 채택이 근본 해법.

### CC-3. 발행 주기 1초 확정 — C 발(發) → A·D 착(着) 🔴 ✅ 결정 완료
**Server C `config.py:23` `SIMULATION_INTERVAL = 1.0초` (5.0→1.0, 사용자 의도 확정 2026-06-30).**
- 한 틱 발행량 ≈ 691(포인트) + 284(장비) ≈ 975건 → 초당 ~195건이 ~975건으로 **5배**.
- 증폭 전파: A `mqtt_service`(SSE 0.5초 배치) 5배, **D `mqtt_worker` → InfluxDB 쓰기 5배(저장/IO 가장 큼)**, 프론트 SSE 트래픽 증가.
- drift/fault_drift는 `interval_seconds/3600` 기반이라 주기 변경에도 물리적 시간당 변화율은 보존됨(원복 불필요).

**1초 확정에 따른 필수 동반 조치 (원복이 아니라 다운스트림 보강):**
1. **D의 CC-2가 P0로 승격** — 1초당 ~975건 ÷ `batch_flush_size=100` = **초당 ~10회 동기(SYNCHRONOUS) write가 이벤트 루프 블로킹**(현 `mqtt_worker.py:84` SYNCHRONOUS, `config.py:60` size=100, interval=5.0). → `run_in_executor`/배치 모드 전환은 이제 선택이 아닌 필수.
2. **D 배치 크기 상향** — `batch_flush_size` 100 → 500~1000으로 올려 write 왕복 횟수 감소(초당 ~10회 → ~1~2회). interval(5초)은 유지 또는 1~2초로 조정.
3. **D InfluxDB 저장/다운샘플 점검** — raw 데이터 5배 증가 → `downsampling.py`/`retention.py`의 `raw_7d` 보존·집계 주기가 5배 볼륨을 감당하는지 확인(D-P2-7 device_state 다운샘플 누락도 함께).
4. **A SSE 큐 누락(A-P1-2) 우선도 상승** — `_event_queue` maxlen 500 < 691 포인트/틱 → 1초마다 ~191건 누락. 1초 체제에서 더 빈번 → Phase 2 내 우선.
5. **문서 동기화** — CLAUDE.md·`_docs/history.md`·MEMORY의 "5초 주기" 서술을 "1초 주기"로 갱신.

> 참고: C 자체의 핫 루프 최적화(C-P0-2 `_find_spec`, CC-2 yield, C-P1 묶음)도 1초 체제에서 5배 더 자주 실행되므로 체감 효과가 커짐.

### CC-4. CORS 와일드카드 + credentials — A·D 공통 🟡
`allow_origins=["*"]`(또는 메서드/헤더 `*`) + `allow_credentials=True` (A main.py:167, D main.py:133-137). 브라우저 스펙상 무효·안티패턴. 운영 시 도메인 화이트리스트.

## 2. 서버별 P0 (횡단 외 단독 이슈)

CC 패턴에 포함되지 않은, 각 서버 고유의 P0:

- **A-P0-2** 무인증 임의 Cypher 실행(`/api/ontology/cypher`). 새니타이저가 `CALL`/`apoc`/`dbms`/`LOAD CSV` 미차단 → 화이트리스트 전환 또는 차단 추가. (CC-1 인증과 결합 처리)
- **A-P0-3** JWT 시크릿 하드코딩 기본값(config.py:44) → 기동 시 기본값이면 실패하도록 강제.
- **B-P0-2** `/command-queue` 상태 API가 항상 0 반환(응답모델↔`get_status()` 키 불일치, command_queue.py:191). 죽은 모니터링 API → 계약 일치.
- **C-P0-2** 핫 루프 `_find_spec` 선형 재탐색 + 함수 내부 import(engine.py:485, profile_factory). spec은 불변 → 프로파일 생성 시 1회 주입, import 모듈 상단 이동.
- **C-P0-3** 691포인트 동기 블로킹(CC-2와 동일 근원).
- **D-P0-1** 동기 InfluxDB I/O(CC-2와 동일 근원).

## 3. 단계별 실행 로드맵

### Phase 1 — 보안 기반 (P0, 의존성 최다) 🔴
> **반드시 4서버 동시 진행** (CC-1은 독립 배포 불가)

1. 공통 인증 가드 설계(Server A↔B↔D 서비스 토큰/세션) → A 프론트 호출부 토큰 주입 동기화
2. A: `/api/chat` 인증+레이트리밋, `/api/ontology/cypher` 인증+새니타이저 강화, JWT 기본값 기동 차단
3. B: 제어 엔드포인트 인증, `userId` 토큰 도출, `ip_address` 실제 기록
4. D: `admin.py` 인증, `acknowledged_by` 토큰 도출
5. ~~CC-3 의도 확인~~ → **✅ 1초 확정**. C `config.py`는 유지, 대신 CC-3의 "필수 동반 조치"(D 배치 보강·문서 동기화)를 Phase 2/문서작업으로 이관.

**성공 기준**: 무인증 요청이 401/403 반환, 프론트 정상 동작(`npm run build` + 수동 curl).
**회귀 위험**: A `fetchJSON`의 401 자동 로그아웃 → 공개 페이지 매핑 선행 필수.

### Phase 2 — 성능/안정성 (P1) 🟠
> 서버별 독립 진행 가능 (CC-2 제외)

- **CC-2**: D InfluxDB I/O `run_in_executor`/배치 모드, C 청크 yield
- A: SSE 이벤트 큐 누락 수정(`_event_queue` maxlen 500 < 691/틱 → 상향 또는 스냅샷 diff), WS+SSE 이중 연결 정리, Neo4j 캐시 확대(토폴로지/장비목록), 에너지 프로파일 `asyncio.gather` 병렬화, OpenAI 타임아웃/max_tokens
- B: 큐 HOL 블로킹 해소(due-time 기반 재큐/워커풀), 큐·감사로그 영속화(`/app/db` 볼륨 활용), httpx 예외 `HTTPError`로 확대, 큐 성공 시 MQTT 발행/감사 누락 보완, 멱등성 키
- C: 핫 루프 최적화(고장 스냅샷 1회, weather 1회, 분류 결과 캐시), device state 변화 시에만 발행
- D: 무제한 `/history` 응답 가드(limit/aggregate), Flux 인젝션 방어(화이트리스트/파라미터 바인딩), write 실패 재시도, `/summary` TTL 캐시

**의존성 주의**: B의 영속화/멱등성(B-P1-2/5)은 **Server C 계약 변경 동반** → B 단독 머지 시 부분 효과.

### Phase 3 — 품질/유지보수 (P2) 🟡
- 공통: CC-4 CORS 도메인 제한, 데드코드 제거
- A: 채팅 응답 페이로드 축소, 프론트 코드 스플리팅(cytoscape/reactflow `dynamic`), `lib/api.ts` 분할
- B: reload 시 BACnet 동기화, GET→POST, `/health` degraded 시 503, BACnet write 값 검증
- C: `stuck_damper` 무효과 수정(또는 문서 제거), 등록 로그 DEBUG 강등, 미사용 코드 정리
- D: `quality` 태그→field 전환(비가역, 신규부터), `alarm_type` 인덱스 추가, `clean_session=False`, device_state 다운샘플, write_api 재사용, 타임스탬프 파서 헬퍼화

## 5. 공통 리스크 / 주의사항

1. **자동화 테스트 부재**(CLAUDE.md 명시) — 모든 변경은 `npm run build`(프론트 타입) + 수동 curl + 로그로 검증. 큐/재시도(B), 인증(전체), 이벤트 루프(C·D) 변경은 회귀 위험 높음 → 최소 단위 테스트 추가 권장.

3. **인증(CC-1)은 4서버 원자적 배포** — 한 서버만 적용 시 호출 체인 단절.
4. **CC-3은 단독 변경 금지** — 플랫폼 차원 파라미터.
5. **문서 동기화** — 변경 후 `_docs/history.md`, `_docs/07_온톨로지_통계_요약.md`, CLAUDE.md, MEMORY 갱신(사용자 선호).
